# PAL Image Uploads Still Tied to Legacy CAPI — Features

## Terms

This glossary applies to `Features.md`, `Services.md`, and `planning-state.md`.

- **PAL** — Post-a-Listing, the KSL sell form in marketplace-frontend.
- **Capi** — the legacy classifieds API, repo `m-ksl-classifieds-api`.
- **ksl-api** — the older legacy API. The Cars endpoints and the old General endpoints live there.
- **vertical** — a listing category with its own code path: Classifieds (General) or Cars.
- **rendition** — a resized or cropped copy of an uploaded image. Today all renditions are pre-generated at upload. "Cut" means "generate a rendition".
- **staging bucket** — a new private GCS bucket. The browser uploads photo bytes there first.
- **signed POST policy** — a GCS upload grant for one object key. Only this grant type can cap upload size and pin metadata.
- **attach** — the step that processes a staged photo and writes its photo doc onto the listing.
- **subscriber** — a Pub/Sub consumer deployment. Each vertical gets its own attach subscriber.
- **photo doc** — the per-photo metadata document in the listing's `photo[]` array in Mongo.
- **poll** — the front end asks GraphQL repeatedly whether a photo is attached.
- **shim** — a legacy endpoint that keeps its route but calls the new path internally.
- **priority rendition** — a rendition cut before attach completes. A **deferred rendition** is cut asynchronously after attach.

## Architecture (chosen solution)

The chosen design is **staged object + async Pub/Sub attach**. The scope decisions are from 2026-09-01, after the shaping meeting with Spencer Dickson, Rebekah Fowles, and Abe Fawson. This design supersedes the staged-object + *synchronous GraphQL commit* design of the [Photo Uploads Architecture design doc](https://app.notion.com/p/3c72ac5cb23580bdbb59f0a6719f9dd0). The doc's mechanics for staging and signed POST policies still apply.

```
Browser ──(1) GraphQL beginListingPhotoUpload────► marketplace-graphql ──► owning vertical's signed-URL endpoint
        ◄── signed POST policy {url, fields, storageKey}                   (GenerateSignedPostPolicyV4; pins the
                                                                            attach contract as x-goog-meta-* fields)
Browser ──(2) multipart POST file bytes──────────► private STAGING bucket  (the only non-GraphQL call)
Bucket  ──(3) OBJECT_FINALIZE ─► Pub/Sub topic
                 ├── classifieds attach subscriber (listing-ps-attach-photo)
                 └── cars attach subscriber        (separate cars deployment)
              subscriber: authz re-check → image-http-rest (by object ref; classified/adPic1 first)
              → $push photo doc onto the listing → remaining renditions cut async → status "done"
Browser ──(4) polls "is it done?" via GraphQL (poll target = Q21) — done means ATTACHED to the listing
Staging object expires via bucket lifecycle rule (backstop; subscriber may delete on success — Q7).
```

**There is no synchronous commit response.** The front end learns the outcome from the poll (the profiles-image precedent). A tile is complete and draggable only after the photo is attached. Per-photo failures must surface through the same poll (Q21). File bytes never travel through GraphQL. The earlier pass rejected this async-attach pattern; the 2026-09-01 decision adopts it. Its trade-offs are now first-class design items: the done-signal mechanism, and photo order under out-of-order arrival (Q19, Q21–Q25).

> **HARD CONSTRAINT: all new endpoints live inside marketplace-backend.** Do not add routes to ksl-api or Capi. A change to the *internals* of a legacy endpoint is allowed — for example, a shim inside `storeListingImage`. Cars image uploads must also be done inside marketplace-backend, not in ksl-api.

> **Definition of done (clarified 2026-09-01):** "Capi/ksl-api image processing eliminated" means that the **PAL/web path no longer calls them**. The Capi upload endpoint stays alive for years as a shim for old mobile apps (F7). This project does not delete legacy endpoints.

## F1. Get signed URL (GraphQL `beginListingPhotoUpload` + per-vertical endpoint)

- Add the mutation `beginListingPhotoUpload(input: {listingId, listingType, filename, contentType, position, replaces, description})`. It returns `{url, fields: JSON!, storageKey}`. The name matches the current convention (`beginProfileImageUpload`, `beginVideoUpload`, `beginJobApplyFileUpload`).
  - `position` is an order hint. Uploads finish out of order. Per the meeting, order rides the upload, not a commit call. `replaces` is optional: the id or URL of a current photo. When set, the upload becomes an edit (F4/F6). `description` applies to Cars only.
  - **This is a separate mutation. Do not reuse `beginProfileImageUpload`.** The profiles mutation ([mutation.profile.graphqls:19-20](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/schema/mutation.profile.graphqls#L19-L20), resolver [begin-profile-image.go](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/mutationresolvers/begin-profile-image.go)) cannot serve listings, for these reasons:
    - Its input is only `mimeType`. There is no listing to authorize or count against.
    - It targets the Profiles image-upload service, with that service's bucket and async pipeline (`IMAGES_SERVICE_URL /image-upload/signed-url`, hardcoded `context: "profile"`). An upload there triggers the profile attach subscriber, the wrong bucket and lifecycle, and no renditions.
    - It creates a profile image-status doc as a side effect.
    - Its `SignedURLResponse` does not contain the `storageKey` that the attach and poll steps need.
    - GraphQL schema changes must be additive-only, so we cannot extend its input.
  - Reuse the *pattern* from `beginJobApplyFileUpload` instead. A generic result type (`{url, fields, storageKey}`) can be shared with future flows.
  - Model: `beginJobApplyFileUpload` — [mutation.job-apply-upload.graphqls](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/schema/mutation.job-apply-upload.graphqls), resolver [job-apply-upload.go](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/mutationresolvers/job-apply-upload.go)
  - Use `@hasRole(role: "MEMBER", useLowSecurity: true)`. Sellers idle on the form. The jobs schema documents this precedent.
  - **The resolver routes by `listingType`** to the owning vertical's signed-URL endpoint: CLASSIFIED → listing-http-rest; CAR → the cars photo deployment (F6). Each vertical then authorizes ownership natively. The GraphQL layer stays a thin proxy.
- Each vertical's backend endpoint generates a **signed POST policy**. Never use a bare signed PUT — only a POST policy can cap size.
  - Model: [listing-jobs-http-rest storage.go:70-121](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-jobs-http-rest/internal/storage/storage.go#L70-L121) — `ConditionContentLengthRange`, a pinned `x-goog-meta-member-id`, custom-time lifecycle.
  - **The policy pins the attach contract as object metadata** (`x-goog-meta-*`): listingId, vertical, memberId, the position hint, optional `replaces`, optional description. The subscriber trusts only server-pinned metadata. It never trusts client-supplied form fields. The exact field list and the validation split are Q22.
  - The object key encodes the uploader: `staging/member/{memberId}/{uuid}` (service and admin scopes per the design doc). The current convention is `staging/{memberId}/{uuid}/{type}.{ext}` ([buildStorageKey](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-jobs-http-rest/internal/storage/storage.go#L208-L211)).
- **A NEW private staging bucket is required.** The serving bucket `gcsb-ddm-images` is public-read with GET-only CORS ([google-storage.tf:11-42](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/media/services/image-http-rest/.tf/google-storage.tf#L11-L42)). TF model: [ksl-jobs-apply-staging bucket](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-jobs-http-rest/.tf/google-storage.tf#L31-L96) — uniform access; POST CORS with an explicit ksl.com origin list (GCS CORS has no wildcards); lifecycle delete on `days_since_custom_time`; an abort rule for incomplete multipart uploads. **The OBJECT_FINALIZE → Pub/Sub notification is now required core infrastructure** — one topic, plus one subscription per vertical subscriber. It is not an optional extra.
- **Enforce the photo-count limit and the rate limit primarily at the get-signed-URL step.** The request then fails before the user spends upload bandwidth. The subscriber re-checks at attach and drops violations. But a dropped photo has no synchronous channel for its error. The enforcement split and its error surfacing are Q23.
- Authorize at get-signed-URL AND re-check at attach. The listing can be deleted, sold, or transferred in between.

## F2. Async attach (per-vertical Pub/Sub subscribers — the intermediary, the majority of the work)

The earlier design placed the attach logic in a synchronous commit endpoint. That logic moves into **per-vertical Pub/Sub subscribers**. They consume the staging bucket's OBJECT_FINALIZE events. Template: [listing-ps-update-video-url](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-ps-update-video-url/app.go#L86-L146). The earlier pass recorded this template as a rejected alternative; it is now adopted. Each subscriber does these steps:

  1. Filter on the object's `vertical` metadata. If the event is not for this vertical: ack and ignore. This is the meeting's "do I care about this one?" model.
  2. Verify the caller and ownership from the pinned metadata. Re-check the listing. A bouncer and an ownership policy exist for classifieds: [validation_middleware.go](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/bouncer/validation_middleware.go), [policy.go:38-64](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/domain/policy.go#L38-L64). Cars does a native `findOne` on `auto` (F6).
  3. Verify the staged object: check the key format, then do a double ownership check. The key-derived memberId must equal the pinned memberId, AND the object metadata must match. Model: [verifyStorageKeyFormat / verifyObjectOwnership](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-jobs-http-rest/internal/storage/storage.go#L213-L294)
  4. Invoke image-http-rest with the object reference and the vertical's rendition split (F3). Cut `classified/adPic1` (the rendition PAL displays) before attach. Defer the other renditions.
  5. Write the photo doc onto the listing with an atomic append. Legacy precedent: `$push` "so we don't overwrite photos added asynchronously" — [GeneralCollection.php:184-238](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Db/Mongo/GeneralCollection.php#L184-L238)
  6. Surface the outcome where the front end's poll can see it (Q21). There is no synchronous response. A partial batch (8 succeed, 3 fail) shows as per-tile status.

- **The attach is idempotent on the staged object name.** This idempotency also serves as the **Pub/Sub redelivery guard**. Delivery is at-least-once, and a redelivered event must not attach twice. The mechanics are Q24.
- **Order under async arrival (reshapes Q19):** the `position` metadata is a hint. Uploads and Pub/Sub deliveries arrive out of order. The recommended shape: **append on arrival; the front end then issues one final `photoOrder` reorder when all tiles are done.** The alternative, a splice via `$push $position`, can interleave wrongly when the array changes between attaches. Stephen Sagers' framing-doc comment still needs a reply that reflects the async design.
- **`photo[]` must stay a dense BSON array. `position` is a sort hint, never a slot index** (Stephen Sagers' 2026-09-01 framing-doc comment; Q19). Out-of-order async arrival makes index-addressed writes *more* tempting. They stay forbidden. Write only via `$push` (optionally with `$position` — a splice cannot create holes), or via a whole-array `$set` for the final order. **Never write an index-addressed `$set photo.N`.** That is the only write shape that null-pads or sparsifies the array. History: PHP `unset` without `array_values` caused it once — Capi fix `ba021453`, patched at [ListingController.php:1741-1743](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Controller/ListingController.php#L1741-L1743). A partial batch failure then yields a *shorter* array, never gaps. The system depends on this invariant for two reasons. First, listing-http-rest's read path hard-fails (500) when `photo` arrives map-shaped (bare `.Decode`, [store/listing.go:157](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/store/listing.go#L157)). Second, PHP stays an active co-writer through the transition — [AbstractCollection.php:90-109](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Db/Mongo/AbstractCollection.php#L90-L109) would explode a sparse array into dotted `photo.N` writes if it is ever wired to listings.
- Carry a correlation identifier from get-signed-URL through attach. Compare the count of signed URLs issued with the count attached: that ratio is the abandonment-rate health metric.

## F3. image-http-rest: source by reference + rendition split (both required)

- Today the service accepts **multipart bytes only** (`r.FormFile("image")` — [app.go:266](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/media/services/image-http-rest/app.go#L266)). Research confirmed that no object-ref or URL source exists. This is net-new work and the single highest-leverage change. It serves the subscribers now and can serve feeds later.
- Add a **storage-object reference** input form `{bucket, object}` next to multipart. The internal read primitive exists: [storage.GetReader/ReadImage](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/services/media/shared-image-packages/storage/storage.go#L162-L194).
- **Rendition split (Q11 — pulled into v1 on 2026-09-01):** the upload call takes a *priority* rendition list. For PAL that list is `classified/adPic1` plus its fallback `classified/mobile_adPic1`. The service cuts the priority list before it returns. It then cuts the other vertical renditions asynchronously, through the current add-renditions path. This is the meeting's answer to Spencer's concern about slow processing: the photo is displayable fast, and the long tail cuts in the background.
  - **Prerequisite (promoted from nice-to-have to required):** `PATCH /image/{id}/renditions` returns 400 for service JWTs today — memberId 0 is hard-rejected ([app.go:663-674](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/media/services/image-http-rest/app.go#L663-L674)). It also re-cuts from the main image. The endpoint must accept service callers and must cut the deferred list correctly.
- **Multipart stays permanently.** These callers require it:
  - The Capi/ksl-api legacy shims. Old mobile apps post multipart for years.
  - Server-generated bytes — for example, the padding step in the jobs migration.
  - Dev, support, and ops curl tools.
- **The external-URL input form is deferred.** It is a feeds optimization only. It is an SSRF surface: it needs host restrictions, blocks on internal ranges and the metadata endpoint, size caps, and timeouts. See design doc §4/§5 and Q6.

- **Edit is a simplified replace (2026-09-01 decision — supersedes the legacy-faithful two-file flow).** The team's own framing: the current editor is destructive — "crop and rotate is a completely new image replacing one" — and no editor state is saved. An edit is therefore **a new image at the old photo's position, and the old image's bytes are deleted after the swap**. Browser path: `beginListingPhotoUpload` with `replaces` → the subscriber processes the new image → it swaps the photo doc at the old photo's index in one atomic operation → it deletes the old files asynchronously. There is no original fetch from GCS. There is no two-file assembly (`image` + `renditionsImage`). There are no `cropMD5`/`userEdit`/`cropTime` stamps. Cache-bust comes free: the replacement *is* a new imageId and URL. **Delete the old bytes only after the swap lands.** The failure direction is then an orphaned new image, never a broken displayed one. This resolves Q20. It deliberately diverges from legacy Capi/cars, which deleted first: [ImageHelper::editImageToImageApi :432-487](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Helper/ImageHelper.php#L432-L487). ## F6. Cars support (separate cars photo deployment — direct write to `classifieds.auto`)

**The 2026-09-01 decision reverses the 8/26 registry resolution of Q5.** Cars gets its **own deployment** in marketplace-backend. From the meeting: "another deployment that is specific to cars… two different deployments… eventually once cars is in classifieds, it just adopts the classifieds thing." The deployment is **deliberately disposable**: it exists until cars data merges into classifieds, and then it retires. It contains the CAR signed-URL endpoint (the F1 route target) and the CAR attach subscriber (F2). It uses the same staging bucket and the same Pub/Sub topic, with its own subscription. The divergence never touches listing-http-rest. It touches GraphQL only through the `listingType` route.

One research correction from the meeting carries forward: cars is **not** "a different Mongo database". Cars listings live in **`classifieds.auto`, on the SAME cluster + database that listing-http-rest uses** (`mplace-mongo.ksl.com/classifieds` — [boosts cron maps cars→`auto`](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-cron-boosts/app.go#L64-L69); [auto-renew reads `general,auto` in prod](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-cron-auto-renew/.tf/kubernetes-deploy.tf#L29-L30)). The new service user still needs a **write grant** on `auto` (Q16). **Elasticsearch sync is free**: a Mongo **change-stream connector** watches `auto` and feeds the cars ES index (`cars-listings`) ([m-ksl-cars-api connector, `fullDocument: updateLookup`](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-cars-api/connector/src/change-identifier.js#L36-L41)). Pub/Sub does **not** feed ES. Correct Mongo writes propagate to ES on their own. Never write ES directly — the connector's merge would clobber it.

**Cars attach operations.** The full side-effect map comes from the [storeListingImage walk :2445-2645](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/ksl-api/public_html/classifieds/cars/api/controllers/ListingController.php#L2445-L2645). On a photo add there are no dealer counters, no modifyTime bump, and no memcache bust.
1. **Check ownership natively.** `findOne` on `auto`. Criteria: a 40-hex id → `{backlot.auctionId}`; else `{id: int}`. Compare the doc's `memberId` to the pinned uploader. No ksl-api read is needed (Q13 resolved).
2. **Call image-http-rest** with the staged ref, and match the legacy call exactly: `vertical: 'classifieds'` (yes — even for cars); **`objectId` = the auctionId string for Backlot**. The generated filename encodes the auctionId, and the `isBacklotPhoto` filter depends on it. Use the Cars 11-rendition list, under the F3 priority/deferred split. Compute **`preMd5` = the MD5 of the raw staged bytes, before processing**. Feeds dedupe on it — "do not remove without written consent from the feeds person".
3. **Write back** with one `findOneAndUpdate` (ReturnDocument: After; 3 attempts, 1s apart). `$push` the exact **10-field cars photo doc**: `id, upload_time (BSON date, snake_case), extension, md5, preMd5, height, width, description, originalFilePath, originalFileName`. There is **no `filterArray`** — that field is Classifieds vocabulary. Update `backlot.photoOrder` in the same write when the listing has `backlot`. Never touch `modifyTime`/`displayTime`/counters — a modifyTime bump re-sorts SRP and re-partitions BigQuery.
4. **Publish `Public_CarsListingEvent`** (project `ddm-platform`). Build the binary `cars.v4.Listing` from the post-update doc, with PubSubVehicle's whitelist semantics: status/newUsed/titleType uppercased; sellerType→DEALERSHIP|FSBO; all times epoch-ms; `backlot` excluded. Swallow publish errors, as legacy does. This event feeds **BigQuery + Google Shopping + dealer-url-scraper — not ES**. A skipped publish delays Shopping eligibility for a listing's first photo. Two new needs: publisher IAM on the externally-owned topic, and a full listing→proto mapping layer, which does not exist in Go yet (Q17). The 10-field photo doc maps 1:1 onto `cars.v4.Listing.Photo` — no proto change is needed. (Q18 resolved: replaced photos keep the same 10-field vocabulary. Cars has no `cropMD5`/`userEdit`. The point is moot anyway: the simplified replace stamps no crop metadata for either vertical.)
5. **History**: insert into `classifieds.autoChangeLog` when status ∈ {Active, Moderate, Stub}. This is audit parity — cheap, recommended.
6. **Edit = the simplified replace (`replaces` metadata).** Process the new image first. Then do **one atomic pull+push in a single `findOneAndUpdate`**. Two round trips would let the change stream observe a transiently empty `photo[]` and blank the ES photos. The pull must also pull `backlot.photoOrder` — otherwise Backlot order breaks silently. Lookups must tolerate http↔https drift on stored ids. **Delete the old bytes only after the swap lands** (GCS URLs → `image-batch-delete`; legacy S3 URLs → the `photosToDelete` queue). This deliberately diverges from legacy, which deleted first (Q20).
7. Surface the outcome to the front end via the same poll mechanism as classifieds (Q21).

Delete and reorder stay on ksl-api's **current** endpoints, via GraphQL. They are unchanged. They are not new endpoints, so the hard constraint allows them. They can migrate to native writes later. Mixed writers on the same `photo` array are safe under Mongo single-document atomicity. The same argument already covers Capi + listing-http-rest on `classifieds.general`.

## F8. Feed-system-ready endpoint contract

The feed system's migration off Capi photo upload is **already designed, and it waits on this project**. Its specs say so explicitly: *"when the Listing Service exposes a photo endpoint in a later tier, only capi.go is swapped out"* ([specs/010 plan.md:201](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/specs/010-feed-system-p1-skeleton/plan.md#L201)). Its dispatch seam ([upstream.go:58-64](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/feeds/services/feeds-ps-syncer/internal/routing/upstream.go#L58-L64)) and its ksl-api client ([kslapi/client.go:8-13](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/feeds/services/feeds-ps-syncer/internal/kslapi/client.go#L8-L13)) document themselves as one-line-swap bridges. The feed migration itself is a later phase. **The F4 endpoints must satisfy this contract now**, so that the later swap is not precluded. **The async browser transport does not touch this contract: feeds keep a synchronous multipart request/response.** Feeds hold bytes server-side and need immediate 4xx/5xx semantics. The staged/async path is browser-only (see F9).

1. **Add** accepts multipart bytes + filename + **`originalFilePath`** (the dealer source URL) + optional `memberId` (the server asserts envelope-vs-listing agreement). `originalFilePath` must round-trip verbatim — it is the feed diff key. The response returns a non-empty canonical URL plus a photo id.
2. **Order**: photos append in call order, and first = primary. An explicit position is strictly better. Feeds upload strictly sequentially per listing to preserve this.
3. **Read-back**: `GET /listing/{id}` keeps `photo[].id` **and** `photo[].originalFilePath` in the response ([listingservice.go:236-239](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/feeds/services/feeds-ps-syncer/internal/routing/listingservice.go#L236-L239); spec 011 FR-130).
4. **Reorder**: keep `PhotoOrder []string` on `PUT /listing/{id}`.
5. **Delete**: per-photo delete, plus delete-all (feeds' `empty_destructive` path). Bonus: per-photo delete plus explicit order lets feeds collapse the **destructive nuke-and-reupload into a targeted diff**. That removes the `PhotoDeleteFailed` mixed-state hazard, which its executor deliberately does not retry ([executor.go:409-415](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/feeds/services/feeds-ps-syncer/internal/domain/executor.go#L409-L415)).
6. **Errors**: a clean 4xx-terminal / 5xx-retriable split, with no substring match. Structured reasons fix today's "Capi collapses the image service's reason into a generic 500" ([outcome.go:254-267](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/feeds/services/feeds-ps-syncer/internal/types/outcome.go#L254-L267)).
7. **Auth**: `Authorization: ddm-jwt <serviceJWT>` — the credential feeds already use for every other listing-http-rest call (service role → privileged, ownership check skipped). This is pure simplification: it retires feeds' `CapiAuth` (~180 lines) and `internal/kslapi/` (~290 lines), plus the `KSL_API_PERSISTENT` secret.
8. **Limits**: set the body cap ≥ feeds' 10MB fetch cap. Note the current 10MB-fetch vs 25MB-Capi mismatch — worth rationalization. The vertical is always `CLASSIFIED` — the feed system has zero Cars code ([artifact/types.go:114-177](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/feeds/services/feeds-ps-syncer/internal/artifact/types.go#L114-L177)).

A bonus payoff: the **jobs-migration processor copies feeds' Capi photo upload verbatim** ([specs/017 research.md:85](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/specs/017-migrate-jobs-listings/research.md#L85)). This endpoint therefore retires **two** Capi photo callers, not one. Source-URL ingestion (image-http-rest fetches the dealer URL itself) stays a separate, measure-first decision (Q6).

## F9. Explicit non-goals

- **Feeds do not use the staged-upload path.** This is a deliberate decision. It is recorded so that nobody "unifies" the paths later. feeds-ps-syncer holds bytes server-side, and a route through staging adds two hops per photo. Feeds will use the **multipart-bytes form** of the F4 endpoints instead — see F8 for the contract.
- **No unification with the profile images-service, and no "media uploader"** (meeting decision, 2026-09-01). Rebekah and Abe proposed a merge of listings with the profiles image manager: t-shirt sizes, plus CDN resize-on-request with a cache, instead of pre-cut renditions — the pattern messages already uses. Chris: "I don't want to worry about trying to change that pattern for listings during this… argue for later". Listings never adopted that pattern, precisely because it is not a drop-in replacement. It is recorded as a candidate future project. This project keeps renditions-on-upload semantics, split per F3.
- **No GraphQL subscriptions, and no websocket completion notify.** The team wants it (Abe: "would be great"), but the particulars were never figured out. jobs-apply cut it for the same reason. The poll design (Q21) must not preclude a later subscription.
- **No "move on while uploading" progress modal.** It needs product buy-off (Spencer). It is a frontend/product follow-up, not this project's scope.
- Listing video URLs are out of scope. The video pipeline is already modern. Abe: nothing meaningful is shared with image processing.
- Dealer logo upload is out of scope. It is still on S3 ([DealerController.php:46-98](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Controller/DealerController.php#L46)).
