# Planning State — PAL Image Uploads Still Tied to Legacy CAPI

Term definitions are in `Features.md` → Terms.

## Identified So Far

**Architecture (chosen solution, reworked 2026-09-01): staged object + async Pub/Sub attach.** The flow: a GraphQL get-signed-URL mutation (`beginListingPhotoUpload`, routed by vertical) returns a signed POST policy. The policy pins the attach contract as object metadata. The browser uploads to a private staging bucket. OBJECT_FINALIZE fires into Pub/Sub. A per-vertical attach subscriber (classifieds / cars) checks authorization, invokes image-http-rest by reference (displayed rendition first), and writes the photo back onto the listing. The front end **polls** for "attached". This design **supersedes the synchronous-GraphQL-commit design** of the earlier passes and of the design doc §3. The sync design's advantages were immediate feedback and no reorder-before-attach race. The poll contract re-creates both: "done" means attached, and the front end does one final reorder. The full feature breakdown is in `Features.md`. The service-by-service changes are in `Services.md`.

**The proposed architecture already exists twice in marketplace-backend.** First: listing-jobs-http-rest — staging keys `staging/{memberId}/{uuid}/...`, a POST policy with a size condition and pinned metadata, storage-key ownership checks, and private-bucket TF with a custom-time lifecycle. Second: the video pipeline — `GenerateSignedPostPolicyV4` signed-URL generation, OBJECT_FINALIZE→Pub/Sub, and a vertical attach subscriber. The video pipeline is now the direct template, not a rejected alternative. The genuinely new work: (a) image-http-rest accepts a source by object reference, plus the priority/deferred rendition split; (b) the attach subscribers plus the service-caller photo endpoints; (c) the separate cars photo deployment.

**Fifth pass (2026-09-01) — shaping-meeting outcomes + scope decisions.** The meeting (transcript in this folder: `PAL image uploads - shaping questions.vtt`; Chris Pies + Spencer Dickson, Rebekah Fowles, Abe Fawson) confirmed these points: signed-URL-via-GraphQL with direct bucket upload (ADR-consistent; videos and profiles are precedent); ksl-api/Capi are thin wrappers around image-http-rest; the FE work is small and wanted (it retires the DR-009 exceptions); explicit order is needed (parallel uploads finish out of order); the stepper blocks "Next"; the editor is a destructive crop/rotate with no saved editor state; videos stay separate. **Chris took four scope decisions after a comparison of the meeting against the package:**
1. **Async Pub/Sub attach** replaces the synchronous commit. This adopts the profiles/video pattern that the earlier pass rejected. It reopens the done signal and photo order as design items → Q21–Q25, and it reshapes Q19.
2. **Separate cars deployment** (reverses Q5's 8/26 registry resolution): an own signed-URL endpoint plus an own attach subscriber. It is deliberately disposable — it retires when cars data merges into classifieds. listing-http-rest stays pure-Classifieds. There is no vertical registry.
3. **Q11's rendition split moves into v1**: cut `classified/adPic1` (+ the mobile fallback) before attach; defer the rest async. This promotes the image-http-rest renditions-PATCH service-JWT fix to required scope.
4. **Simplified replace edit**: an edit is a new image at the old photo's position, and the old bytes are deleted after the swap. There is no two-file assembly and no `cropMD5`/`userEdit`/`cropTime`. This resolves Q8/Q18/Q20. Classifieds and Cars edits become identical.

**In-meeting non-goals recorded (F9):** no unification with the profile images-service / "media uploader" (t-shirt sizes + CDN resize-on-request — "argue for later"); no GraphQL subscriptions for completion (poll first, do not preclude); no move-on-while-uploads-run progress modal (needs product buy-off). **Definition of done clarified:** legacy "elimination" means the PAL/web path stops its use of Capi/ksl-api. The Capi endpoint lives on as a shim for old apps. **Correction:** cars is not "a different Mongo database" — it is `classifieds.auto`, on the same cluster and DB.

The only feed "dedupe" is a photo-count comparison ([FileProcessor.php:464-470](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classfeeds/FileProcessor.php#L464-L470)). Cars image uploads must also be done inside marketplace-backend. The separate cars deployment satisfies this — it lives in marketplace-backend.

- Rendition lists exist in 3 divergent legacy copies. The geometry is already central, in image-http-rest's rendition-recipes.go.
- Order is implicit array position everywhere (`photoOrder` = a URL list).
- Photo identity is the URL string. The "id" wire key is marked do-not-rename.
- `fields.Photos` is a silent no-op on the listing-rest path in marketplace-graphql. A commit mutation no longer fixes it — close it independently (see Services §1).
- deletePhoto is pinned to CAPI until listing-http-rest gains a per-photo delete.
- The CAPI→listing-rest rollout gate (the `use_listing_rest` family) is the prior art for rollout.
- Old mobile apps require the Capi/ksl-api upload endpoints as shims for years. The shims stay synchronous multipart — never via staging.
- `gcsb-ddm-images` is public-read and GET-only, so a new private staging bucket is mandatory.
- GraphQL schema changes must be additive-only.

**Third-pass findings (2026-08-26, marketplace-backend-only constraint):**
- **Cars listings = Mongo `classifieds.auto`, on the SAME cluster and database that listing-http-rest already uses** (`mplace-mongo.ksl.com/classifieds`). - **Cars photo doc corrections**: 10 fields (`id, upload_time (snake, BSON date), extension, md5, preMd5, height, width, description, originalFilePath, originalFileName`) — **no `filterArray`** (that field is Classifieds-only vocabulary). `preMd5` = the MD5 of the raw uploaded bytes (the feed dedupe key — "do not remove without written consent from the feeds person"). The legacy cars upload calls image-http-rest with `vertical:'classifieds'`, and **`objectId` = the auctionId string for Backlot** (the filename encodes it; `isBacklotPhoto` depends on it). History: a `classifieds.autoChangeLog` insert when status ∈ {Active, Moderate, Stub}. A replace-at-index must be **one atomic pull+push** (the change stream would see an empty `photo[]` and blank ES), and it must pull `backlot.photoOrder` too.
- Features F6 condenses the full 10+7-item replication checklist for a Go writer.

**Fourth-pass finding (2026-09-01, commit-position concern verified):** Stephen Sagers (the design-doc author) left an unresolved comment on the framing doc (2026-09-01). His concern: commit-with-position could produce non-sequential numbers in the photo array, which PHP would then serialize as a map. **Research verified the scenario as unreachable through the proposed write shapes.** No code in Capi, ksl-api, or listing-http-rest writes `photo.<N>` by numeric index. Every write is `$push`/`$pull` or a whole-dense-array `$set`. `$push`+`$position` is a splice and cannot create holes. A partial batch failure yields a *shorter dense array*, never gaps. Photo identity is the `id` field everywhere, never the index. The bug he remembered is his own 2020 fix (Capi `ba021453`): PHP `unset()` without `array_values()` before a whole-field `$set` → BSON document keys "0","2","3" → a `json_encode` map. The patch survives at [ListingController.php:1741-1743](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Controller/ListingController.php#L1741-L1743) (ksl-api mirror :1803-1804). Residual hazards are recorded in Features F2: (a) PHP stays an active writer through the transition — a PHP edit that loses its `array_values()` re-introduces the bug, and latent machinery in [AbstractCollection.php:90-109](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Db/Mongo/AbstractCollection.php#L90-L109) would explode a sparse array into dotted `photo.N` `$set`s if it is ever wired to listings; (b) Go's read path **hard-fails (500) on a map-shaped `photo`** — a bare `.Decode` at [store/listing.go:157](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/store/listing.go#L157), with no tolerance shim. That blast radius is why the dense-array invariant carries load. Decision handle: Q19 (reshaped for async — see below; the invariant analysis holds unchanged, and out-of-order async arrival makes it *more* important).

**Legacy behavior contract captured** (details and line refs in `Features.md`):
- A synchronous per-image response with a URL (legacy only — the new browser path is poll-based).
- ~7 pre-generated renditions (Classifieds) / 11 (Cars).
- An atomic `$push` append.
- Edit-in-place with cropMD5/userEdit/cropTime, a new-URL cache-bust, and async old-file cleanup. (2026-09-01: the crop metadata is deliberately dropped — simplified replace.)
- Reorder by URL list, with a fuzzy filename match.
- A dual-path delete (GCS batch-delete vs the legacy-S3 queue).
- Cars extras: the `backlot.photoOrder` parallel array, a per-photo `description`, `preMd5`, ES sync via the change stream, and **no server-side edit flow**. (See the `CAR_pal_photo_editor` finding above — the client-side fake makes the edit a live requirement.)
