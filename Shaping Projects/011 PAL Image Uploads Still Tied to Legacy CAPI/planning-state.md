# Planning State — PAL Image Uploads Still Tied to Legacy CAPI

## Identified So Far

**Architecture chosen (working solution):** staged object + GraphQL commit, per the [Photo Uploads Architecture design doc](https://app.notion.com/p/3c72ac5cb23580bdbb59f0a6719f9dd0). A GraphQL get-signed-URL mutation (`beginListingPhotoUpload`) returns a signed POST policy → browser uploads to a private staging bucket → GraphQL commit by `storageKey` + position → listing-side endpoint does authz, invokes image-http-rest, writes back to the listing, returns URLs synchronously. Full feature breakdown in `Features.md`; service-by-service changes in `Services.md`.

**The proposed architecture already exists twice in marketplace-backend** — listing-jobs-http-rest (staging keys `staging/{memberId}/{uuid}/...`, POST policy w/ size condition + metadata pinning, storage-key ownership verification, private-bucket TF with custom-time lifecycle) and the video pipeline (`GenerateSignedPostPolicyV4` signed-URL generation, OBJECT_FINALIZE→Pub/Sub, vertical attach subscriber). The genuinely new work: (a) image-http-rest accepting a source by object reference, (b) the listing-side photo endpoints (the intermediary — the bulk of the work), (c) the CAR leg of the photo registry (`carPhotoService` + thin ksl-api metadata endpoints).

**Design-doc open questions answered by research:**
- *Which rendition does the sell form display?* → `?filter=classified/adPic1`, onError fallback `classified/mobile_adPic1`, both verticals ([Photos.tsx:273-289](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-frontend/apps/ksl-marketplace/app/sell/post-a-listing/components/Photo/Photos.tsx#L273-L289)).
- *The "two-file edit flow"* is server-side behavior, not a client contract: the browser sends only the edited JPEG; **Capi downloads the original back from GCS** and posts both to image-http-rest ([ImageHelper.php:432-487](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Helper/ImageHelper.php#L432-L487)). Cache-busting = image-http-rest generating a new imageId.
- *Does a listing always exist when photos are staged?* In the current FE flow yes — `addPhoto(listingId, …)` requires it, and PAL creates a stub first (`createListing`/`createCarListingStub`). Binding a listingId at the get-signed-URL step is therefore viable today (confirm no future pre-listing staging flow — Q12).
- *MD5-based duplicate detection*: **does not exist in the legacy repos** — md5/preMd5/cropMD5 are computed and stored, never compared. The only feed "dedupe" is a photo-count comparison ([FileProcessor.php:464-470](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classfeeds/FileProcessor.php#L464-L470)). Downstream consumers unknown (Q9).

**Cross-repo bug insight (high value):** ksl-api General's rendition list is missing `classified/adPic1` — the exact rendition PAL displays — and General feed photos upload through ksl-api. Varnish returns 200 + opaque XML for missing renditions (no `onError`). ⇒ Feed-sourced listings likely show broken photos in PAL today; matches the reverted `filterArray` fix (sc-389434 / revert e157c4524 in marketplace-frontend). Recorded as nice-to-have fix + Q4.

**HARD CONSTRAINT (user, 2026-08-26): all new endpoints must live inside marketplace-backend** — no new ksl-api/Capi routes (shimming existing legacy endpoints' internals is allowed). Cars image uploads must be accomplished within marketplace-backend.

**Key constraints inventoried:** rendition lists exist in 3 divergent legacy copies (geometry already centralized in image-http-rest's rendition-recipes.go); ordering is implicit array position everywhere (`photoOrder` = URL list); photo identity = URL string ("id" wire key marked do-not-rename); `fields.Photos` is a silent no-op on the listing-rest path in marketplace-graphql; deletePhoto is pinned to CAPI until listing-http-rest gains a per-photo delete; the CAPI→listing-rest rollout gate (`use_listing_rest` family) is the prior art for rollout; old mobile apps require the Capi/ksl-api upload endpoints to live on as shims for years; `gcsb-ddm-images` is public-read GET-only so a new private staging bucket is mandatory; GraphQL schema changes must be additive-only.

**Second-pass findings (2026-08-26, Cars-through-listing-rest rework):**
- **Cars photo editing is in flight**: unmerged branch `feature-pal-use-new-photo-editor-sc-392495` (commit 3b349abc1, 2026-08-26, no PR) enables the PAL editor for Cars behind Remote Config `CAR_pal_photo_editor` (+ `CAR_pal_redesign_allowed_ids`, stepper flow only), faking replace-in-place client-side (add → delete → reorder, duplicate left on partial failure). No server-side Cars edit exists in any repo. The new `EditPhoto` path gives Cars a real atomic replace (Features F6).
- **listing-http-rest has no vertical concept** (store hard-bound to Mongo `classifieds.general*`, domain typed on `ClassifiedListing`) — but already calls ksl-api with nonce auth (`location.go:126`) and binds the same `global_ksl_api_nonce_*` secrets feeds uses. Divergence design: `internal/photo` `PhotoService` registry keyed by typed Vertical (patterns: in-service `policy.Registry`, dealer-http-rest `VerticalUpdater`, asset-http-rest Vertical enum, vehicle-details-rest ksl-api client + ownership gate). See Features F4/F6.
- **Feeds migration is pre-designed on the feeds side** (specs 010/011/013: "only capi.go is swapped out"); the binding artifact for this project is the F8 endpoint contract (bytes + `originalFilePath` round-trip, first=primary ordering, `id`+`originalFilePath` read-back, per-photo delete + delete-all, 4xx/5xx split, ddm-jwt). Feeds is Classifieds-only — zero Cars code. The jobs-migration processor copies feeds' Capi upload verbatim, so the endpoint retires two Capi photo callers.

**Third-pass findings (2026-08-26, marketplace-backend-only constraint):**
- **Cars listings = Mongo `classifieds.auto` on the SAME cluster+database listing-http-rest already uses** (`mplace-mongo.ksl.com/classifieds`). Prod Go read precedents exist (boosts cron maps cars→`auto`; auto-renew reads `general,auto`; favorites reads `autoFavorites`). No Go service *writes* cars data today — boosts proxies cars to ksl-api ("extra dealer logic") and dealer-http-rest's cars updater is commented out ("not ready"); for **photo adds specifically** the full side-effect surface is mapped in Features F6 (no dealer counters, no modifyTime, no memcache bust).
- **Cars ES sync is a Mongo change-stream connector** (`m-ksl-cars-api/connector*` watching `auto`, fullDocument:updateLookup) — NOT Pub/Sub. Direct Mongo writes reach ES automatically; never write ES directly. `publishListingState` → `Public_CarsListingEvent` (binary `cars.v4.Listing`, project ddm-platform, topic owned by ksl-api TF) feeds **BigQuery/Pinpoint + Google Shopping + dealer-url-scraper**; photo add publishes today, delete/editDescription don't (topic already lossy). Google Shopping drops 0-photo listings → first-photo publish matters.
- **Cars photo doc corrections**: 10 fields (`id, upload_time (snake, BSON date), extension, md5, preMd5, height, width, description, originalFilePath, originalFileName`) — **no `filterArray`** (Classifieds-only vocabulary); `preMd5` = MD5 of raw uploaded bytes (feed dedupe key — "do not remove without written consent from the feeds person"). Legacy cars upload calls image-http-rest with `vertical:'classifieds'` and **`objectId` = auctionId string for Backlot** (filename encodes it; `isBacklotPhoto` depends on it). History: `classifieds.autoChangeLog` insert when status ∈ {Active, Moderate, Stub}. Replace-at-index must be **one atomic pull+push** (change stream would see empty `photo[]` and blank ES) and must pull `backlot.photoOrder` too.
- The full 10+7-item replication checklist for a Go writer is condensed into Features F6.

**Legacy behavior contract captured** (details + line refs in `Features.md`): synchronous per-image response with URL; ~7 pre-generated renditions (Classifieds) / 11 (Cars); atomic `$push` append; edit-in-place with cropMD5/userEdit/cropTime + new-URL cache-bust + async old-file cleanup; reorder by URL list with fuzzy filename match; delete dual-path (GCS batch-delete vs legacy-S3 queue); Cars extras: `backlot.photoOrder` parallel array, per-photo `description`, `preMd5`, ES sync via `publishListingState`, and **no server-side edit flow** (but see the in-flight `CAR_pal_photo_editor` finding above — the client-side fake makes edit a live requirement).
