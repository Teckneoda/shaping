## Identified So Far

**Architecture (chosen solution, reworked 2026-09-01): staged object + async Pub/Sub attach.** The flow: a GraphQL get-signed-URL mutation (`beginListingPhotoUpload`, routed by vertical) returns a signed POST policy. The policy pins the attach contract as object metadata. The browser uploads to a private staging bucket. OBJECT_FINALIZE fires into Pub/Sub. A per-vertical attach subscriber (classifieds / cars) checks authorization, invokes image-http-rest by reference (displayed rendition first), and writes the photo back onto the listing. The front end **polls** for "attached". This design **supersedes the synchronous-GraphQL-commit design** of the earlier passes and of the design doc §3. The sync design's advantages were immediate feedback and no reorder-before-attach race. The poll contract re-creates both: "done" means attached, and the subscriber splices each photo at its pinned position (Q19, 2026-09-02 — no final reorder call). The full feature breakdown is in `Features.md`. The service-by-service changes are in `Services.md`.

**The proposed architecture already exists twice in marketplace-backend.** First: listing-jobs-http-rest — staging keys `staging/{memberId}/{uuid}/...`, a POST policy with a size condition and pinned metadata, storage-key ownership checks, and private-bucket TF with a custom-time lifecycle. Second: the video pipeline — `GenerateSignedPostPolicyV4` signed-URL generation, OBJECT_FINALIZE→Pub/Sub, and a vertical attach subscriber. The video pipeline is now the direct template, not a rejected alternative. The genuinely new work: (a) image-http-rest accepts a source by object reference, plus the priority/deferred rendition split; (b) the attach subscribers plus the service-caller photo endpoints; (c) the separate cars photo deployment.

**Fifth pass (2026-09-01) — shaping-meeting outcomes + scope decisions.** The meeting (transcript in this folder: `PAL image uploads - shaping questions.vtt`; Chris Pies + Spencer Dickson, Rebekah Fowles, Abe Fawson) confirmed these points: signed-URL-via-GraphQL with direct bucket upload (ADR-consistent; videos and profiles are precedent); ksl-api/Capi are thin wrappers around image-http-rest; the FE work is small and wanted (it retires the DR-009 exceptions); explicit order is needed (parallel uploads finish out of order); the stepper blocks "Next"; the editor is a destructive crop/rotate with no saved editor state; videos stay separate. **Chris took four scope decisions after a comparison of the meeting against the package:**

2. **Separate cars deployment** (reverses Q5's 8/26 registry resolution): an own signed-URL endpoint plus an own attach subscriber. It is deliberately disposable — it retires when cars data merges into classifieds. listing-http-rest stays pure-Classifieds. There is no vertical registry.
3. **Q11's rendition split moves into v1**: cut `classified/adPic1` (+ the mobile fallback) before attach; defer the rest async. This promotes the image-http-rest renditions-PATCH service-JWT fix to required scope.
4. **Simplified replace edit**: an edit is a new image at the old photo's position, and the old bytes are deleted after the swap. There is no two-file assembly and no `cropMD5`/`userEdit`/`cropTime`. This resolves Q8/Q18/Q20. Classifieds and Cars edits become identical.

**Fourth-pass finding (2026-09-01, commit-position concern verified):** Stephen Sagers (the design-doc author) left an unresolved comment on the framing doc (2026-09-01). His concern: commit-with-position could produce non-sequential numbers in the photo array, which PHP would then serialize as a map. **Research verified the scenario as unreachable through the proposed write shapes.** No code in Capi, ksl-api, or listing-http-rest writes `photo.<N>` by numeric index. Every write is `$push`/`$pull` or a whole-dense-array `$set`. `$push`+`$position` is a splice and cannot create holes. A partial batch failure yields a *shorter dense array*, never gaps. Photo identity is the `id` field everywhere, never the index. The bug he remembered is his own 2020 fix (Capi `ba021453`): PHP `unset()` without `array_values()` before a whole-field `$set` → BSON document keys "0","2","3" → a `json_encode` map. The patch survives at [ListingController.php:1741-1743](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Controller/ListingController.php#L1741-L1743) (ksl-api mirror :1803-1804). Residual hazards are recorded in Features F2: (a) PHP stays an active writer through the transition — a PHP edit that loses its `array_values()` re-introduces the bug, and latent machinery in [AbstractCollection.php:90-109](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-classifieds-api/src/Db/Mongo/AbstractCollection.php#L90-L109) would explode a sparse array into dotted `photo.N` `$set`s if it is ever wired to listings; (b) Go's read path **hard-fails (500) on a map-shaped `photo`** — a bare `.Decode` at [store/listing.go:157](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/store/listing.go#L157), with no tolerance shim. That blast radius is why the dense-array invariant carries load. Decision handle: Q19 (reshaped for async — see below; the invariant analysis holds unchanged, and out-of-order async arrival makes it *more* important).
