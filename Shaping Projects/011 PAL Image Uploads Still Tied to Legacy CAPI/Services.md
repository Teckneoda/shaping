## 1. marketplace-graphql — begin mutation + poll query + client

**Created:**
- The `beginListingPhotoUpload` mutation. It returns a signed upload POST policy — `{url, fields: JSON!, storageKey}`. The name matches the `begin*Upload` convention. Auth: `@hasRole(role: "MEMBER", useLowSecurity: true)`. The input carries `listingId, listingType, filename, contentType, position, replaces?, description?`. The resolver **routes by `listingType`** to the owning vertical's signed-URL endpoint (CLASSIFIED → listing-http-rest §2; CAR → cars deployment §4). It stays a thin proxy. Template: [mutation.job-apply-upload.graphqls](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/schema/mutation.job-apply-upload.graphqls), resolver [job-apply-upload.go](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/mutationresolvers/job-apply-upload.go). This is a **new mutation** — `beginProfileImageUpload` cannot be reused. Reasons: it targets the profile pipeline's backend and bucket, it has side effects, its `mimeType`-only input cannot be extended additively, and its response has no `storageKey`. See Features F1.
- A **status poll query** — the front end's "is it done?" signal. It replaces the synchronous response of the earlier commit mutation. Q21 decides what it reads: the listing's photo array, or a per-upload status doc (the profiles precedent). Its shape must not preclude a later GraphQL subscription (an F9 non-goal, deferred).
- ~~Commit mutation~~ / ~~Edit mutation~~ — **dropped (2026-09-01 async decision)**. An edit is `beginListingPhotoUpload` with `replaces` (Features F4). This changes the Q2 landscape: the `fields.Photos` silent no-op on the listing-rest path ([listing_mapping.go](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/mutationresolvers/listing_mapping.go#L23-L138) never maps Photos) is no longer fixed by a commit mutation. Close it independently: document the field, or reject it.
- A new client package `services/listing-photos/`, per repo conventions: cookie forwards via [forwardAuthCookies](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/services/listing-rest/client.go#L750-L777), `applyServiceAuth` (ddm-jwt), sentinel errors + `ClientError`, spans `marketplace-graphql-<Client>-<Method>`.

**Constraints:** The GraphQL layer proxies only. It never generates signed policies itself, and it holds no business logic (repo CLAUDE.md). `@hasRole` enforces MEMBER only; admin and on-behalf-of need explicit checks (pattern: [resolveLifecycleMemberIDArg](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-graphql/graph/mutationresolvers/classifieds_listing_lifecycle.go#L119-L128)). Schema changes must be additive-only, because mobile apps cannot be force-updated. Decide the routing-gate behavior (Q1). The repo uses spec-kit — this work lands as `specs/003-*`, with a `contracts/*.graphqls`.

## 2. listing-http-rest — CLASSIFIED signed-URL + service-caller endpoints

**Created:** The CLASSIFIED get-signed-URL endpoint. It generates the signed POST policy and pins the attach-contract metadata (Features F1). Also the **service-caller multipart endpoints**: add, replace, per-photo delete, delete-all (Features F4 table; callers: feeds F8, jobs-migration, the Capi shim, GraphQL `deletePhoto`). Reorder exists ([update.go:296-299](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/domain/update.go#L296-L299), `reorderPhotos` :394-419). **The browser add path does not call these endpoints** — it goes staging bucket → subscriber (§3).

**Structure:** The earlier `PhotoService` vertical registry is **dropped** — cars never enters this service (2026-09-01 decision; Features F4/F6). listing-http-rest stays pure-Classifieds. Its store is hard-bound to Mongo `classifieds.general*`, and that is now acceptable. Put the attach logic in a package that the §3 subscriber can share — one implementation, two triggers (Q25).

**Reused in place:** the bouncer middleware + the ownership policy + `requireVerifiedEmail`; `ImageClient` (extend it beyond DeleteImage — [image.go:34-71](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/client/image.go#L34-L71)); the cleanup-sidecar shape ([mediacleanup.go](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/sidecar/mediacleanup.go), [purgecleanup.go](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/sidecar/purgecleanup.go)); the `Photo` type, which already models the full legacy doc ([listing.go:796-814](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/types/listing.go#L796-L814)).

**New responsibilities:** Classifieds rendition-list ownership (the priority and deferred lists, Features F3). Write-back failure reconciliation — when the image processes but the listing write fails, an orphaned image record remains. The simplified-replace semantics: swap the doc at the index, and delete the old bytes only after the swap (Features F4).

## 3. `listing-ps-attach-photo` — classifieds attach subscriber (NEW)

This is the CLASSIFIED leg of Features F2. Template: [listing-ps-update-video-url](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-ps-update-video-url/app.go#L86-L146). It consumes the staging bucket's OBJECT_FINALIZE events on its own subscription and filters `vertical == CLASSIFIED`. Then, in order:
1. Verify the staged object + ownership (model: [verifyStorageKeyFormat / verifyObjectOwnership](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-jobs-http-rest/internal/storage/storage.go#L213-L294)).
2. Call image-http-rest by reference, with the priority rendition list.
3. `$push` the photo doc (dense-array invariant, Features F2).
4. Surface the status for the FE poll (Q21).

The attach is idempotent on the staged object name — that is the Pub/Sub redelivery guard (Q24). It handles `replaces` as the simplified atomic swap.

## 4. Cars photo deployment — separate, disposable (NEW)

**The 2026-09-01 decision reverses Q5's 8/26 registry resolution:** cars photo handling gets its **own deployment** in marketplace-backend — the CAR signed-URL endpoint + the CAR attach subscriber — per the meeting sketch ("two different deployments… eventually cars adopts the classifieds thing"). It is deliberately disposable: it retires when cars data merges into classifieds. The full operation list is in Features F6. Highlights:
- **Ownership + existence checked natively**: `findOne` on `classifieds.auto` — the same cluster/DB the platform already uses ([boosts maps cars→`auto`](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-cron-boosts/app.go#L64-L69); prod read precedent: auto-renew, favorites). New: a **write grant** on `auto` for the deployment's Mongo user (Q16 — re-scoped from listing-http-rest's user to the new deployment's user).
- **image-http-rest by reference**, with the Cars rendition list ([rendition-recipes.go:58-116](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/media/services/image-http-rest/domain/renditions/rendition-recipes.go#L58-L116)) under the priority/deferred split. Legacy-exact params: `vertical:'classifieds'`, Backlot `objectId` = the auctionId string, `preMd5` of the raw bytes.
- **Write-back**: `$push` the 10-field cars photo doc (+ `backlot.photoOrder`) via `findOneAndUpdate` ×3. A replace is **one atomic pull+push** — two writes would let the change stream blank the ES photos. Delete the old bytes only after the swap (Q20). Legacy-S3 deletions queue to `classifieds.photosToDelete`. Insert the `autoChangeLog` history row.
- **Publish `Public_CarsListingEvent`** — the full `cars.v4.Listing`, built from the post-update doc. It feeds BigQuery + Google Shopping, NOT ES. New work: the listing→proto mapping layer + publisher IAM on the externally-owned topic (Q17). The publisher plumbing itself is ~10 lines on the current [pubsub publisher](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-http-rest/internal/pubsub/publisher.go).
- **ES is hands-off**: the [m-ksl-cars-api change-stream connector](file:///Users/cpies/code/shaping/Research%20Repos/Legacy/m-ksl-cars-api/connector/src/change-identifier.js#L36-L41) owns `cars-listings`. Never write it directly.
- No ksl-api client is needed for the photo path. Delete and reorder stay on the current ksl-api endpoints via GraphQL. They can migrate later.

## 6. Staging bucket + Pub/Sub (NEW infra)

A private GCS bucket, with Terraform: uniform bucket-level access; POST/PUT/OPTIONS CORS with explicit ksl.com origins; `ConditionContentLengthRange` in the policies; a custom-time lifecycle delete measured in hours (orphans are the normal case); an abort rule for incomplete multipart uploads. **Required (async decision): the OBJECT_FINALIZE → Pub/Sub notification — one topic, one subscription per vertical subscriber (§3, §4).** Full template: [listing-jobs-http-rest/.tf/google-storage.tf](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-jobs-http-rest/.tf/google-storage.tf) and [.tf/pubsub.tf](file:///Users/cpies/code/shaping/Research%20Repos/marketplace-backend/apps/listing/services/listing-jobs-http-rest/.tf/pubsub.tf). Staged bytes are attacker-controlled: the bucket is never public, its objects are never served directly, and content is validated on read. Subscribers trust only the policy-pinned `x-goog-meta-*` metadata (Q22).
